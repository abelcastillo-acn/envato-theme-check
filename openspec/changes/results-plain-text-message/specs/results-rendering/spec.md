## Purpose

Present Theme Check findings grouped by severity with counts, per-finding selection and collapsible evidence, so a reviewer can scan a run and choose what goes into the author message.

## ADDED Requirements

### Requirement: Findings SHALL be grouped by severity with counts
The results page SHALL render one section per severity present, in the order REQUIRED, WARNING, RECOMMENDED, INFO, each with a heading showing the severity label and the number of findings in it, plus a summary line with all four counts.

#### Scenario: Mixed run
- **WHEN** a run produces 3 REQUIRED, 5 WARNING and 12 INFO findings
- **THEN** the page shows sections "REQUIRED (3)", "WARNING (5)", "INFO (12)" in that order, no RECOMMENDED section, and a summary "REQUIRED 3 · WARNING 5 · RECOMMENDED 0 · INFO 12"

#### Scenario: Clean run
- **WHEN** a run produces no findings
- **THEN** the existing "passed the tests" heading and success box are shown and no group sections or message panel are rendered

### Requirement: Each finding SHALL be individually selectable
Every finding SHALL have a checkbox that controls whether it is included in the author message. Findings of severity REQUIRED, WARNING and RECOMMENDED SHALL be checked by default; INFO findings SHALL be unchecked by default. The default set SHALL be configurable in the message template.

#### Scenario: Default selection
- **WHEN** the results page loads
- **THEN** all REQUIRED/WARNING/RECOMMENDED checkboxes are checked and all INFO checkboxes are unchecked

#### Scenario: Group toggle
- **WHEN** the reviewer clicks the checkbox in a group heading
- **THEN** every finding in that group is checked or unchecked accordingly, and the group checkbox shows an indeterminate state when only some are selected

#### Scenario: Toolbar shortcuts
- **WHEN** the reviewer clicks "Select all", "Select none" or "Select REQUIRED"
- **THEN** the selection updates accordingly and the message preview regenerates

### Requirement: Evidence lines SHALL be collapsible
Line excerpts attached to a finding SHALL be rendered inside a collapsible element whose summary states the number of matching lines; a toolbar action SHALL expand or collapse all evidence at once.

#### Scenario: Finding with three matching lines
- **WHEN** a finding carries excerpts for lines 12, 40 and 77
- **THEN** its evidence is collapsed by default with the summary "3 matching lines" and expands on click to show the three excerpts

### Requirement: Severity SHALL be conveyed by text and colour
The severity label SHALL be rendered as a text badge in addition to colour, with text/background contrast of at least 4.5:1, and all interactive controls SHALL be keyboard-operable with a visible focus indicator.

#### Scenario: Keyboard-only navigation
- **WHEN** a reviewer tabs through the results page
- **THEN** every checkbox, summary and button receives focus in order and shows a visible focus ring

### Requirement: Finding markup SHALL survive output filtering
The message body of each finding SHALL continue to be filtered with the existing allowlist (`li`, `span[class]`, `strong`, `code`, `pre`, `a[href]`); the wrapper element carrying the finding id, severity and rule id SHALL be generated by the renderer and SHALL not be subject to that filter.

#### Scenario: Legacy finding with a link
- **WHEN** a legacy check emits a message containing `<a href="https://…">…</a>` and `<strong>file.php</strong>`
- **THEN** the link and bold text render, and the wrapper still exposes the finding id and severity to the script

### Requirement: Findings data SHALL be exposed to the page script
The results page SHALL embed a JSON block containing the theme name, version, slug, run date and the list of findings (`id`, `severity`, `label`, `check`, `text`, `file`, `lines[]`), encoded so it cannot terminate the script element.

#### Scenario: Message containing "</script>"
- **WHEN** a finding text contains the literal string `</script>`
- **THEN** the JSON block is still well-formed and the page script parses it successfully

### Requirement: INFO suppression SHALL keep working
The existing "Suppress INFO" form option SHALL continue to remove INFO findings from the page and from the data block.

#### Scenario: Suppress INFO checked
- **WHEN** the reviewer submits the form with "Suppress INFO" checked
- **THEN** no INFO section is rendered and the JSON block contains no INFO findings

### Requirement: Legacy Trac output mode SHALL be removed
The hidden "trac" option and the `<textarea>` output mode SHALL no longer exist; the results page SHALL always render the grouped view.

#### Scenario: Request with trac parameter
- **WHEN** a POST includes `trac=1`
- **THEN** the parameter is ignored and the grouped results view is rendered
